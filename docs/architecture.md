# Architecture

## Overview

Cadence is a single Next.js 15 (App Router) application serving both the
frontend and the backend API (via Route Handlers) — the same shape as
before the pivot, since that decision had nothing to do with the product
being SAT prep specifically.

The product runs entirely on free infrastructure by design: live
transcription uses the browser's built-in Speech Recognition API (no
Deepgram, no API key), and coaching feedback is generated by a rule-based
engine (no Claude/Anthropic API, no API key). Everything works with zero
external accounts and zero cost, at the tradeoff of somewhat approximate
word-level timing (see below) and templated rather than freshly-written
coaching prose.

```
Browser mic
  ├─ Web Audio API (AnalyserNode) ── local pitch/volume sampling, no network
  └─ Browser Speech Recognition API (SpeechRecognition / webkitSpeechRecognition)
     — live transcript, chunked into finalized phrases as you speak
                                              │
                              Browser approximates per-word timestamps by
                              spreading each finalized phrase's words across
                              an estimated speaking-rate window, then computes
                              live WPM / filler words from them
                              (pure functions, src/lib/speech-metrics.ts)
                                              │
                              on stop: full transcript + computed metrics
                                              │
                                              ▼
                                   POST /api/speech/sessions (Next.js)
                                              │
                              stores session, recomputes metrics
                              server-side (authoritative), generates
                              rule-based coaching feedback
                                              │
                                              ▼
                                   Full report returned to browser
```

**Why not Deepgram?** The original design streamed audio to Deepgram's
live WebSocket API for real word-level timestamps. That's a better source
of truth, but Deepgram (like every hosted STT API) isn't free forever —
and the product requirement is genuinely $0, no card, no trial. The
browser's own `SpeechRecognition` API costs nothing and needs no account,
at the cost of only giving us finished phrases rather than per-word
timing. `use-speech-session.ts` approximates word timestamps by assuming a
baseline speaking rate and spreading each phrase's words across the time
window between when it started and when the browser finalized it — good
enough for pace/filler/pause scoring, but an approximation, not a
measurement, and documented as such in that file.

**Why not Claude for coaching feedback?** Same reasoning — the Anthropic
API has no free tier. `coaching.service.ts` generates strengths/
weaknesses/action-plan/drills from the already-computed scores via a rule
set instead: less varied in phrasing than an LLM would produce, but every
session still gets real, specific, accurate feedback, and it can never
fail (no network call at all).

`src/lib/speech-metrics.ts` is a shared, pure-function module (no I/O),
used both client-side (for live in-progress scores while speaking) and
server-side (to authoritatively recompute the final scores that actually
get stored — client-reported numbers are never trusted directly).

## Layering

- **`src/app/**`** — pages and API route handlers. Route handlers stay
  thin: validate input, call a service function, translate the result into
  an HTTP response via `src/lib/api-handler.ts`.
- **`src/server/**`** — domain logic, organized by area (`server/auth/`,
  `server/speech/`). No HTTP awareness — throws `AppError` on failure, unit
  testable without spinning up routes.
- **`src/lib/**`** — cross-cutting utilities, including `speech-metrics.ts`
  (the scoring math) and `audio-analysis.ts` (pitch/volume DSP) — both
  isomorphic, safe to import client- or server-side.
- **`src/components/**`** — UI, organized by feature (`layout`,
  `marketing`, `auth`, `practice`, `reports`).
- **`src/hooks/**`**, **`src/services/**`**, **`src/stores/**`** — client
  data layer. `use-speech-session.ts` is the most involved hook: it owns
  the mic-permission → SpeechRecognition → live-metrics state machine for
  an in-progress recording.

## Auth model

Unchanged from before the pivot — this part of the app is fully generic.
JWT access token (15 min, `jose`) + rotating opaque refresh token (30 days)
in httpOnly cookies. See `src/server/auth/**` and `src/lib/auth-server.ts`.
Middleware does a cheap cookie-presence check for UX; real enforcement is
`requireUser()` on every protected route/page.

## Scoring approach (why rule-based, not "AI magic")

Confidence, pace, and vocal-variety scores are computed from real, measured
signals — not a trained ML model (there's no labeled training data to train
one on, and pretending otherwise would make the scores unexplainable,
which the product explicitly should never do):

- **WPM**: word count ÷ elapsed minutes, from the (approximated) word
  timestamps described above.
- **Filler words**: dictionary match against the transcript, with
  timestamps.
- **Pauses**: gaps between consecutive word timestamps, classified as
  natural / long / awkward by duration.
- **Pitch & volume variance**: sampled client-side via the Web Audio API's
  `AnalyserNode` (~every 150ms) — this part is a real, precise measurement
  regardless of the STT approximation above, since it reads the raw audio
  signal directly. Tracked for coefficient of variation.
- **Confidence score**: a weighted composite of the above, with a
  generated explanation naming exactly which factors moved the score.

The qualitative coaching report (strengths, weaknesses, action plan,
drills) is generated by a rule set in `coaching.service.ts` keyed off the
same computed scores — see the "Why not Claude" note above.

## Error handling contract

Unchanged: every API response is `{ data: T }` or
`{ error: { code, message } }`, via `withErrorHandling` in
`src/lib/api-handler.ts`.
